# Microsoft Entra enterprise identity

The principal configures optional enterprise sign-in in **Team & safety**, confirms sensitive access, and records a reason. Native owner sign-in and the existing owner second factor remain available for recovery. A required enterprise policy keeps staff denied during an outage or after disconnection.

Configure `ENTRA_TENANT_ID`, `ENTRA_CLIENT_ID`, `ENTRA_CLIENT_SECRET` and an independent random `ENTRA_TRANSACTION_SECRET` of at least 32 characters as server bindings. Never enter their values in source, browser forms or logs. Use a tenant-specific application, register this installation's origin followed by `/auth/oidc/enterprise/callback`, and grant the application permission to read its organization through Microsoft Graph. Activation verifies client credentials and the returned organization before changing policy. No mailbox access is requested.

When provider MFA is required, [configure the optional `amr` ID-token claim](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims) and enforce MFA in Entra. Only a cryptographically verified `mfa` assertion satisfies the provider requirement. Missing assertions are refused when that policy is selected. Otherwise the existing Blotter factor policy applies. Provider MFA never grants a sensitive-administration step-up by itself.

Save and invite each practice member first. The principal explicitly associates their email with their independently verified, application-specific OIDC `sub`. An Entra directory object ID is not that subject. Email claims never select an account, and provisioning cannot create unknown people or manage the principal. The sign-in page offers Microsoft Entra after activation.

The principal maps a provider group reference to a preparer or reviewer role and an existing client access team. An identity with no mapped group has no practice access. When mappings disagree, the preparer role wins; client teams may overlap. Existing direct principal grants remain separate. Manage-access delegation does not permit enterprise administration.

Issue the provisioning token once and configure the installation origin followed by `/scim/v2` as the provider endpoint. Only its digest is stored. Rotation invalidates the old token. The supported transport follows [Microsoft's SCIM user and group provisioning shapes](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups): filtered and paginated user and group reads; associated-user activation and deactivation; group creation, replacement and membership patches; deletion. Provision the group with its mapped reference as `externalId`. Configure user attribute mappings for userName, active, displayName and externalId. Other user attributes are not synchronized. Immutable user associations cannot be changed through SCIM. Disabled identities lose memberships; reactivation needs an explicit group grant again.

Every provisioning or mapping change recomputes managed roles and team memberships, invalidates managed browser sessions and credential versions, revokes their agent keys and records attribution. A member signs in again after a membership change. Open work and historical authorship remain intact; use native offboarding to transfer responsibilities. The provisioning token cannot read client data, issue invites or change firm settings.

Archives retain the reviewed policy and mapping history, with connections and identities inactive, and omit provisioning digests and session assurance. The destination principal recreates excluded native accounts, independently reviews the associations and reconnects before staff access resumes. Owner erasure requires typing `ERASE ENTERPRISE` and a reason; it removes associations, mappings and provisioning authority, revokes managed staff, and advances the native erasure journal so stale archives are refused.

Current proof is the built-Worker enterprise lifecycle integration journey and its desktop and phone browser journey. The separately invoked live journey verifies the held tenant's client-credential connection, organization read, provisioning refusal after disconnection, native owner recovery and erasure. Interactive tenant-user sign-in and Entra-driven provisioning still require an authorized sandbox user and provisioning configuration; documented network shapes alone do not prove those provider operations. No Microsoft 365 mailbox or SharePoint site is required by this identity clause.
